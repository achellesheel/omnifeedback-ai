V3 · A Second Bug, Found Live

A friend testing the app found what 27 passing tests couldn't

Same sentence, scored MEDIUM under V2
↓ switch model version, nothing else ↓
Correctly scored HIGH / CRITICAL under V3

V2 scored an obviously-critical complaint ("crashes every time I check out, I've switched to a competitor") almost identically to an obviously-positive one. Tests check code correctness — not whether a model actually generalizes to language it never saw in training.

Root Cause, Measured

196 words. That's V2's entire vocabulary.

Out-of-vocabulary rate: template-matching text vs. real-world phrasing.

V2's BiLSTM learns its own embedding table from scratch — its vocabulary is exactly 196 words, because the synthetic training templates are narrow. Tokenizing genuinely natural sentences showed 33–63% of words mapping to <UNK>. With over half a sentence invisible, the model has almost nothing to work with — output collapses toward the training mean regardless of true severity.

The Fix

Don't learn English from scratch — fine-tune what already knows it

Same lesson from an unrelated image-classification project: fine-tuning a slice of a pretrained model beat training a CNN from scratch by a wide margin. Applied here: fine-tune a pretrained DistilBERT instead of training a BiLSTM's vocabulary from 4,000 rows.

Subword tokenization means no closed-vocabulary problem at all — any English word decomposes into known pieces.

Shipping It

The checkpoint was too big for GitHub

265MB saved (full model state dict) — exceeds GitHub's 100MB hard limit
↓
56MB — only the fine-tuned subset (last 2 layers + head); frozen backbone re-downloaded from HuggingFace at load time

~79% of that 265MB was the frozen, unmodified DistilBERT backbone — identical to what AutoModel.from_pretrained() already fetches fresh. Rather than reach for Git LFS, saved only the parameters that actually changed and reconstructed the rest at load time.

Verified byte-for-byte identical predictions before and after the change — a storage fix, not a retrain.
Honest Boundary

Severe ≠ CRITICAL — and that's worth saying plainly

Tested ~20 real sentences directly against V3 to find what actually crosses the 0.8 CRITICAL threshold. Two patterns reliably do:

0.860"deleted all data... fix immediately... unacceptable"
0.808"unauthorized access... password changed... financial risk"
A genuinely severe complaint outside those two patterns — e.g. "production down, losing revenue every minute" — tops out around 0.69–0.79 (HIGH), not CRITICAL. The threshold is calibrated to specific training patterns, not a general "how bad does this sound" scale. Expected behavior for a model trained on a particular distribution — not a bug — but worth stating plainly rather than letting a viewer assume otherwise.

Data Insights II

Most errors are boundary cases, not failures

False negatives

Almost entirely the deliberately-ambiguous "neutral" template class (urgency 0.35–0.6) — the model lands on the wrong side of a boundary the dataset was built to contain, not a comprehension failure.

An honest limitation

Channel vs. urgency independence: χ²=4.18, p=0.840. The synthetic generator assigns channel independent of content — a real gap, documented and fixed in the roadmap, not hidden.
