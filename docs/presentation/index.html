THE PROJECT

The problem, and the solution I applied

A feedback triage platform, built so that its own metrics can be trusted.

The problem

  • Too much feedback, too many channels. Twitter, email, reviews, call notes and in-app comments pile up faster than anyone can read them.
  • Urgent complaints get buried. A “double charged, fix this now!” looks like any other ticket until someone reads it.
  • Metrics can lie. My first model scored a perfect 1.0, but it had only memorised 9 sentences.

What I built

  • Triage: an urgency score from 0 to 1 for every item.
  • Themes: unsupervised clustering of what customers talk about.
  • Resolution: a GenAI copilot that drafts root cause, action and a reply, plus entity extraction and executive summaries.

Same pipeline, three versions: the fix made visible

V1 · NAIVE
1.0

F1 and silhouette are perfect, but there are only 9 unique sentences. Memorisation.

V2 · HARDENED
0.33

Varied, noisy data gives honest scores. But its own 196-word vocabulary fails on real wording: separation 0.02.

V3 · TRANSFER
0.30

A pretrained DistilBERT separates critical from positive about 13× better, on the same data.

The ideaDon't just report a good number. Show why a number can be misleading, then fix the cause (data first, model second), and prove it on real text.

What I took from it

  • A perfect metric deserves suspicion; check the data before the model.
  • Fix a generalisation problem with the right tool: here, pretrained knowledge.
  • Build in a fallback so a demo never fails, but make the fallback visible.

  • One shared risk-threshold constant: the code currently uses five different cut-offs.

  • Run data_insights.py on held-out rows only (it is in-sample today).
